## 一、模块目标

边缘模型运行模块接收已经生成的 `PerceptionResult`，输出统一的 `EdgeResult`。

模块内部提供两条运行路线：

```text
LocalModelRunner      本地模型执行器
CodeFallbackRunner    代码替代执行器
```

任务编排器不需要知道当前走哪条路线，只调用统一的模型运行入口。

## 二、启动时选择运行路线

不要每处理一个数据包就重新查找模型。应在边缘服务启动时检测一次：

```text
读取本地模型路径
→ 检查模型文件是否存在

不存在：
→ execution_mode = CODE_FALLBACK
→ 使用代码替代执行器

存在：
→ 尝试加载模型
→ 执行一次最小可用性检查

加载和检查成功：
→ execution_mode = LOCAL_MODEL
→ 使用本地模型执行器

加载或检查失败：
→ 记录失败原因
→ execution_mode = CODE_FALLBACK
→ 使用代码替代执行器
```

这里建议把“存在但无法加载”也转入代码路线，否则仍然不能保证项目完整跑通。

## 三、本地模型路线

```text
接收PerceptionResult
→ 转换成模型需要的输入
→ 执行本地模型推理
→ 解析模型输出
→ 校验输出结构和取值
→ 生成统一EdgeResult
```

本节只需要说明：

- 使用哪些 `PerceptionResult`字段作为模型输入；
- 模型文件路径和版本从配置读取；
- 模型输出必须经过校验；
- 模型不得修改输入的 `PerceptionResult`。

不需要重复降采样、特征计算和数据质量规则。

## 四、代码替代路线

代码路线不是重新实现感知模块，而是使用已有的 `PerceptionResult`，通过简单、固定、可重复的判断规则生成 `EdgeResult`：

```text
接收PerceptionResult
→ 读取特征、工况和质量状态
→ 执行固定判断规则
→ 生成与模型路线结构一致的EdgeResult
→ 校验EdgeResult
```

代码路线应满足：

- 不使用随机结果；
- 相同输入必须得到相同输出；
- 输出结构与模型路线完全相同；
- 明确标记这是代码替代结果，不能冒充真实模型结果；
- 规则集中配置，不散落在流程代码中。

第一阶段不需要追求代码判断有多准确，它的主要作用是保证整条处理链、接口、状态和摘要流程能够跑通。

## 五、运行期间的模型异常

即使启动时模型加载成功，运行期间也可能推理失败。为了符合“始终可以跑通”的目标，建议：

```text
本地模型推理成功
→ 返回模型结果

本地模型推理异常或输出非法
→ 记录模型错误
→ 当前包改用CodeFallbackRunner
→ 代码路线成功后返回统一EdgeResult

两条路线都失败
→ 返回success=false
→ error_code=MODEL_INFERENCE_FAILED
```

模型出错但代码路线成功时，不应把当前数据包判定为处理失败；但必须记录本次降级，方便以后排查。

## 六、统一输出

两条路线最终都返回同一个 `EdgeResult`，建议至少能够区分来源：

| 字段 | 含义 |
|---|---|
| `edge_result` | `normal`、`warning`或`fault` |
| `confidence` | 模型置信度或代码规则分数 |
| `edge_risk_level` | 风险等级 |
| `execution_mode` | `LOCAL_MODEL`或`CODE_FALLBACK` |
| `runtime_version` | 实际使用的模型版本或代码规则版本 |

代码路线的 `confidence`只能解释为规则分数，不能描述为经过训练和校准的模型置信度。

## 七、整个流程

```text
边缘服务启动
→ 检测并加载本地模型
→ 选择LOCAL_MODEL或CODE_FALLBACK
→ 保存当前execution_mode

收到PerceptionResult
→ 调用当前执行器
→ 生成EdgeResult
→ 校验EdgeResult
→ 返回任务编排器
```
