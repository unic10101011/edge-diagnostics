当前阶段按理想连续传输场景实现，假设数据发送器每50 ms发送一包、不发生丢包且同一sender_id的数据按发送顺序到达。文档保留NOT_RECEIVED、PACKET_NOT_RECEIVED和missing_sequence_numbers等异常处理接口，作为防御性处理及后续非理想网络场景的扩展入口；这些接口不属于当前正常处理主线。

实现任务注册表和任务状态机、任务编排器
任务分配：一定成功，固定ACCEPTED
等待和执行：一定不超时
内部处理：一个任务包含80个数据包。
单包处理失败只影响当前数据包，不导致整个任务失败。
每个数据包无论成功或失败都必须产生一条处理摘要。
80个预期序号位置全部进入终态并生成摘要后，整个任务进入COMPLETED。

当前数据发送约定：

1. 一个任务固定包含80个序号位置；
2. 每个任务只有一个数据发送器；
3. sequence_number固定为1～80；
4. 数据发送器严格按照sequence_number递增发送；
5. 数据包不会乱序到达；
6. sequence_number=80同时作为数据发送结束标志；
7. 第80包必须可靠到达；
8. 普通缺失数据包不补发。
9. 模型加载一定成功

验收：

- 一个任务可以连续接收并处理80个数据包；
- 每个数据包都建立独立处理记录；
- 单包校验失败不会停止后续数据包；
- 校验失败的包不进入环形缓存、降采样、感知和模型；
- 每个数据包无论成功还是失败都生成摘要；
- 重复数据包不会重复处理；
- 收到sequence_number=80后能够确认发送结束；
- 能够根据1～80与实际接收序号确认缺失包；
- 缺失包不进入环形缓存和处理链；
- 每个缺失序号都生成NOT_RECEIVED记录和缺失摘要；
- 所有实际收到的包处理结束、缺失摘要生成后，任务进入COMPLETED。

# 一、整体运行逻辑
```text

调度器下发一个包含80包的任务
→ 边缘建立TaskRecord
→ task_status = WAITING_FOR_INPUT
→ 返回ACCEPTED
→ 调度器通知数据发送器发送80包数据

每收到一个数据包：
收到sequence_number=1～79：
→ 正常建立PacketRecord并处理
→ task_status保持RUNNING

收到sequence_number=80：
→ 正常建立PacketRecord并处理第80包
→ 标记end_sequence_received=true
→ 计算missing_sequence_numbers
→ 为缺失序号建立NOT_RECEIVED记录
→ 为缺失序号生成缺失摘要
→ 等待所有已收到数据包进入包级终态
→ 检查terminal_packet_count是否等于80
→ 检查summary_generated_count是否等于80
→ 两个条件都满足
→ task_status=COMPLETED

当前包校验失败：
→ 生成校验失败摘要
→ packet_status = VALIDATION_REJECTED
→ 继续处理下一包

当前包处理成功：
→ 生成正常摘要
→ packet_status = SUCCEEDED
→ 继续处理下一包

当前包后续处理失败：
→ 生成处理失败摘要
→ packet_status = PROCESSING_FAILED
→ 继续处理下一包

80个序号位置都生成摘要后，任务进入COMPLETED。
```
调度任务字段表：
| 字段 | 类型 | 含义 |
|---|---|---|
| `task_id` | string | 任务唯一编号 |
| `target_edge_node_id` | string | 调度器选定的目标边缘节点 |
| `input_ref` | object | 任务级输入范围 |
| `input_ref.sender_id` | string | 数据发送器编号 |
| `input_ref.expected_packet_count` | integer | 本任务预计接收的包数，当前为80 |
| `dispatched_at_ns` | integer | 调度器发出任务的时间 |
示例：
```json
{
  "task_id": "task_000001",
  "target_edge_node_id": "edge_01",
  "input_ref": {
    "sender_id": "sender_01",
    "expected_packet_count": 80
  },
  "dispatched_at_ns": 1784784400300000000
}
```
约定每个任务的sequence_number为 1~80
每个实际数据包继续携带自己的packet_id和sequence_number

# 二、任务注册表
每收到一个调度任务，就登记一条记录

每条任务记录至少保存：

| 字段 | 含义 |
|---|---|
| `task_id` | 任务唯一编号 |
| `target_edge_node_id` | 目标边缘节点 |
| `sender_id` | 数据发送器编号 |
| `expected_packet_count` | 预计包数，当前为80 |
| `task_status` | 整个任务状态 |
| `received_at_ns` | 收到任务时间 |
| `acknowledged_at_ns` | 返回`ACCEPTED`时间 |
| `started_at_ns` | 第一包开始处理的时间 |
| `finished_at_ns` | 全部包结束的时间 |
| `received_packet_count` | 已收到的唯一数据包数 |
| `received_sequence_numbers` | 实际收到的唯一序号集合 |
| `terminal_packet_count` | 已得到终态结果的预期序号位置数量 |
| `successful_packet_count` | 成功处理的包数 |
| `validation_rejected_count` | 校验失败的包数 |
| `processing_failed_count` | 后续处理失败的包数 |
| `summary_generated_count` | 已生成摘要的包数 |
| `end_sequence_received` | 是否已经收到`sequence_number=80` |
| `missing_sequence_numbers` | 缺失序号列表 |
| `missing_packet_count` | 已确认缺失的序号数量 |
| `data_completeness` | 当前任务的数据完整性 |
| `output` | 任务级汇总结果 |

data_completeness取值：
| 值 | 含义 |
|---|---|
| `PENDING` | 尚未收到第80包，不能确认完整性 |
| `COMPLETE` | 收到第80包且1～80全部存在 |
| `INCOMPLETE` | 收到第80包后确认存在缺失 |

received_packet_count只统计实际收到的唯一数据包，缺失包不能计入received_packet_count。

计数关系：
```text
missing_packet_count = missing_sequence_numbers的数量

terminal_packet_count
= successful_packet_count
+ validation_rejected_count
+ processing_failed_count
+ missing_packet_count
```

任务必须成功写入注册表后，边缘才能向调度器返回ACCEPTED。

# 三、数据包处理记录

每收到一个唯一数据包，建立一条 PacketRecord。
| 字段 | 含义 |
|---|---|
| `task_id` | 所属任务 |
| `packet_id` | 数据包编号 |
| `sender_id` | 数据发送器编号 |
| `sequence_number` | 在任务中的顺序 |
| `packet_status` | 当前数据包状态 |
| `current_stage` | 当前包正在执行的处理阶段 |
| `received_at_ns` | 数据包到达时间 |
| `finished_at_ns` | 数据包处理结束时间 |
| `error_code` | 当前包失败错误码 |
| `edge_output` | 当前包的边缘模型结果 |
| `summary_generated` | 当前包是否已生成摘要 |
检查：同一task_id中，一个sequence_number只能对应一个packet_id

缺失包处理记录字段：
| 字段 | 缺失包取值 |
|---|---|
| `packet_id` | `null`，禁止编造 |
| `sender_id` | 任务中的发送器编号 |
| `sequence_number` | 缺失的序号 |
| `packet_status` | `NOT_RECEIVED` |
| `current_stage` | `null` |
| `received_at_ns` | `null` |
| `finished_at_ns` | 确认缺失的时间 |
| `error_code` | `PACKET_NOT_RECEIVED` |
| `edge_output` | `null` |
| `summary_generated` | 缺失摘要生成后为`true` |

| `current_stage` | 含义 |
|---|---|
| `VALIDATION` | 校验当前数据包 |
| `RAW_CACHE` | 将当前包写入环形缓存 |
| `DOWNSAMPLING` | 对当前包降采样 |
| `PERCEPTION` | 对当前包预处理和提取特征 |
| `MODEL_INFERENCE` | 对当前包执行边缘模型 |
| `SUMMARY_BUILD` | 为当前包生成摘要 |
使用规则：
```text
- current_stage属于PacketRecord；
- 只在packet_status=PROCESSING时使用；
- 编排器在调用包处理模块前修改current_stage；
- 当前包进入终态后，current_stage设为null。
```

PacketRecord主键为：
(task_id, sequence_number)

packet_id是实际数据包身份字段，不作为唯一主键。
缺失包的packet_id可以为null。

# 四、任务状态机
任务状态机规定：一个任务可以从什么状态变成什么状态，以及哪些转换不允许发生。

状态机相当于一个交通规则，可以校验一个状态能否转变成另一个状态。
转换的规则：
RECEIVED
→ WAITING_FOR_INPUT
→ RUNNING
→ COMPLETED

任务状态字段表：
| 状态 | 含义 |
|---|---|
| `RECEIVED` | 边缘刚收到任务 |
| `WAITING_FOR_INPUT` | 任务已接受，尚未收到第一包 |
| `RUNNING` | 正在接收或处理80包数据 |
| `COMPLETED` | 80个预期序号位置均已进入终态并生成摘要 |
COMPLETED是任务终态，只表示80个预期序号均得到明确处理结果，不表示80包全部校验成功。

# 五、数据包状态机
| `packet_status` | 含义 |
|---|---|
| `RECEIVED` | 当前包已经到达 |
| `PROCESSING` | 当前包正在处理 |
| `SUCCEEDED` | 当前包处理成功 |
| `VALIDATION_REJECTED` | 当前包严格校验失败 |
| `PROCESSING_FAILED` | 校验通过，但后续模块失败 |
| `NOT_RECEIVED` | 收到第80包后，确认该序号的数据包没有到达 |
转换规则：
RECEIVED
→ PROCESSING
→ SUCCEEDED / VALIDATION_REJECTED / PROCESSING_FAILED

在收到第80包后，由任务编排器直接为缺失序号创建的终态记录：缺失序号→ 创建PacketRecord→ packet_status = NOT_RECEIVED

# 六、任务编排器
## 1. 接收调度任务，检查：
- task_id 是否存在；
- target_edge_node_id 是否是当前节点；
- input_ref 是否完整；
- 是否为重复或冲突任务。
然后把任务写入任务注册表。
当前阶段假设调度任务内容合法，检查仅用于确认字段并登记任务，不设计任务拒绝分支。

任务写入注册表并进入WAITING_FOR_INPUT后，固定返回：
ack_status = ACCEPTED
reason_code = null

任务确认表：
| 字段 | 当前阶段取值 |
|---|---|
| `task_id` | 对应任务编号 |
| `edge_node_id` | 当前边缘节点 |
| `ack_status` | 固定为`ACCEPTED` |
| `reason_code` | 固定为`null` |
| `received_at_ns` | 收到任务时间 |
| `acknowledged_at_ns` | 返回确认时间 |

## 2. 匹配任务和原始数据
根据task_id查询任务
→ 检查task_status为WAITING_FOR_INPUT或RUNNING
→ 检查sender_id与任务一致
→ 检查sequence_number在1～80范围内，且没有冲突
→ 检查当前task_id内的packet_id没有重复
→ 检查sequence_number没有对应其他packet_id
→ 原子建立PacketRecord
→ packet_status = RECEIVED
→ received_sequence_numbers加入当前sequence_number
→ received_packet_count + 1
→ packet_status = PROCESSING
→ current_stage = VALIDATION
→ 提交当前包处理流程

第一包到达：WAITING_FOR_INPUT → RUNNING
后面第2～80包到达时：task_status继续保持RUNNING

重复和冲突规则：
```text
- 相同task_id和sequence_number已经存在：
  不重复建立PacketRecord；

- 相同task_id和sequence_number对应不同packet_id：
  记录TASK_SEQUENCE_CONFLICT；

- 相同packet_id出现在不同sequence_number：
  记录PACKET_CONTENT_CONFLICT。
```
## 3. 发送结束与缺失确认
收到sequence_number=80后，任务编排器执行：

expected_sequence_numbers = {1, 2, ..., 80}
missing_sequence_numbers
= expected_sequence_numbers - received_sequence_numbers

如果missing_sequence_numbers为空：
data_completeness = COMPLETE

如果missing_sequence_numbers非空：
data_completeness = INCOMPLETE

对每个缺失序号：
```text
1. 创建packet_status=NOT_RECEIVED的PacketRecord；
2. error_code=PACKET_NOT_RECEIVED；
3. 不调用校验、环形缓存、降采样、感知和模型；
4. 生成processing_status=packet_missing的摘要；
5. missing_packet_count加1；
6. terminal_packet_count加1；
7. summary_generated_count加1。
```

## 4. 按顺序调用处理模块
任务进入 RUNNING 后，编排器按照固定顺序调用：
```text
数据校验→ 原始环形缓存→ 降采样→ 感知处理→ 边缘模型→ 包摘要生成
```
## 5. 统一处理错误
任何模块失败后，只停止当前数据包的后续处理，不影响任务中的其他数据包。
内部模块只需要报告：是否成功、错误码

校验失败：
```text
保存校验错误码
→ 保持packet_status = PROCESSING
→ current_stage = SUMMARY_BUILD
→ 生成校验失败摘要
→ summary_generated = true
→ summary_generated_count + 1
→ current_stage = null
→ packet_status = VALIDATION_REJECTED
→ validation_rejected_count + 1
→ terminal_packet_count + 1
```

后续模块失败：
```text
保存错误码
→ 保持packet_status = PROCESSING
→ current_stage = SUMMARY_BUILD
→ 生成处理失败摘要
→ summary_generated = true
→ summary_generated_count + 1
→ current_stage = null
→ packet_status = PROCESSING_FAILED
→ processing_failed_count + 1
→ terminal_packet_count + 1
```

内部处理错误码表：

| 错误码 | 含义 | 当前包处理 |
|---|---|---|
| `RAW_CACHE_WRITE_FAILED` | 通过校验的完整原始包写入环形缓存失败 | 停止当前包后续处理，进入`PROCESSING_FAILED` |
| `DOWNSAMPLING_FAILED` | 当前包在抗混叠滤波或降采样过程中失败 | 停止感知和模型推理，进入`PROCESSING_FAILED` |
| `PERCEPTION_FAILED` | 当前包在预处理、质量判断或特征提取过程中失败 | 停止模型推理，进入`PROCESSING_FAILED` |
| `MODEL_INFERENCE_FAILED` | 边缘模型执行当前包推理时发生异常 | 不生成有效边缘推理结果，进入`PROCESSING_FAILED` |
| `MODEL_OUTPUT_INVALID` | 模型输出缺少必要字段、格式错误或取值不合法 | 拒绝使用该模型结果，进入`PROCESSING_FAILED` |

统一处理规则：
```text
出现上述任一错误时，只停止当前数据包的处理，不影响其他数据包。
当前包的edge_output设为null，保存对应error_code，生成处理失败摘要，
然后processing_failed_count、terminal_packet_count和summary_generated_count分别加1。
```

当前阶段假设边缘模型已经成功加载，不设计`MODEL_LOAD_FAILED`及模型恢复流程。

## 6. 处理成功
成功包的完整计数流程：
```text
边缘模型生成合法结果
→ 保持packet_status = PROCESSING
→ current_stage = SUMMARY_BUILD
→ 生成正常摘要
→ summary_generated = true
→ summary_generated_count + 1
→ current_stage = null
→ packet_status = SUCCEEDED
→ successful_packet_count + 1
→ terminal_packet_count + 1
```

## 7. 返回最终结果
任务进入COMPLETED必须同时满足：
```text
1. end_sequence_received = true；
2. 所有实际收到的数据包均已进入包级终态；
3. 所有缺失序号均已建立NOT_RECEIVED记录；
4. terminal_packet_count = expected_packet_count = 80；
5. summary_generated_count = expected_packet_count = 80。
```
最终结果示例：
```json
{
  "task_id": "task_000001",
  "task_status": "COMPLETED",
  "data_completeness": "INCOMPLETE",

  "expected_packet_count": 80,
  "received_packet_count": 79,
  "missing_packet_count": 1,
  "missing_sequence_numbers": [37],

  "successful_packet_count": 76,
  "validation_rejected_count": 2,
  "processing_failed_count": 1,

  "terminal_packet_count": 80,
  "summary_generated_count": 80
}
```
缺失摘要说明：
```json
{
  "summary_generated_at_ns": 1781920804010000000,
  "summary_id": "summary_task_000001_seq_37",
  "task_id": "task_000001",
  "packet_id": null,
  "sender_id": "sender_01",
  "sequence_number": 37,
  "processing_status": "packet_missing",
  "error_code": "PACKET_NOT_RECEIVED",
  "features": null,
  "edge_inference": null
}
```
## 8. 清理临时数据
每个数据包进入终态后：
- 释放该包的计算副本和临时对象；
- 保留PacketRecord；
- 校验成功且环形缓存写入成功的原始包，继续按照保留时间保存在环形缓存中；
- 校验失败的包不进入环形缓存；
- 保留失败摘要。
缺失包：
- 不存在计算副本；
- 不进入环形缓存；
- 保留NOT_RECEIVED PacketRecord；
- 保留缺失摘要。

整个任务进入COMPLETED后：
- 保留TaskRecord和80条PacketRecord；
- 具体清理时间后续确定。
