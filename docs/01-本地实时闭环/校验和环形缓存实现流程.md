声明：
- 本模块接收任务接入和数据匹配模块提交的已匹配唯一数据包。重复包、未收到包和身份冲突包已在上游处理，不会进入本模块，也不会建立ContextSlot。
- 当前阶段采用理想连续传输前提：数据发送器每50 ms发送一个数据包，不发生丢包，同一sender_id的数据按照发送顺序到达边缘。新旧任务之间的数据流保持连续，任务切换不清空上下文队列。

整篇文档的顺序可以概括为：

```text
收到数据包
→ 把已匹配的数据包加入上下文队列
→ 严格校验
→ 写入原始缓存
→ 云端需要时查询前20包
→ 定期淘汰旧数据
```

# 一、把已匹配的数据包加入上下文队列
整体流程：
```text
准备建立ContextSlot
→ 检查end_generate_timestamp_ns
（end_generate_timestamp_ns必须存在、类型为整数且大于0；当前不与received_at_ns比较。）

合法：
→ ContextSlot.end_generate_timestamp_ns = 原值
→ cache_status = PENDING
→ 追加到队尾
→ 继续严格数据校验

缺失或非法：
→ ContextSlot.end_generate_timestamp_ns = null
→ cache_status = VALIDATION_REJECTED
→ raw_packet_ref = null
→ 追加到队尾
→ 返回success=false
→ error_code = INVALID_TIMESTAMP
→ 不再执行后续严格校验、缓存、降采样、感知和模型
```
## 1. `ContextSlot`输入前提
本模块只接收任务接入和数据匹配模块提交的已匹配唯一数据包。任务匹配、身份字段检查、重复包、未收到包和身份冲突已由上游处理，本模块不重复判断。每收到一个上游提交的数据包，就为其建立一个ContextSlot。

ContextSlot包含字段：
| 字段 | 含义 | 用途 |
|---|---|---|
| `task_id` | 当前包所属任务 | 追踪包来自哪个任务，不用于过滤上下文 |
| `packet_id` | 当前原始数据包编号 | 与采集结束时间共同核对锚点身份 |
| `sequence_number` | 当前包在原任务中的序号 | 排错和追踪，不表示跨任务接收顺序 |
| `end_generate_timestamp_ns` | 当前采样窗口结束时间；缺失或非法时为null | 与packet_id共同定位和核对锚点 |
| `received_at_ns` | 边缘实际接收当前包的本地时间 | 确定队列接收顺序、计算保留时长和淘汰过期数据 |
| `cache_status` | 当前包的原始数据缓存状态 | 判断能否提供完整原始数据 |
| `raw_packet_ref` | 原始缓存查询句柄或缓存键 | 在原始缓存中读取完整原始包 |

cache_status字段及其含义表：
| 状态 | 含义 |
|---|---|
| `PENDING` | 已加入队列，正在校验或写入缓存 |
| `AVAILABLE` | 校验通过，完整原始包已经写入缓存 |
| `VALIDATION_REJECTED` | 建立ContextSlot时的时间戳检查或后续严格校验失败，没有保存原始包 |
| `CACHE_WRITE_FAILED` | 校验通过，但完整原始包写入失败 |

raw_packet_ref与状态的对应关系：
```text
PENDING
→ raw_packet_ref = null

AVAILABLE
→ raw_packet_ref必须有效

VALIDATION_REJECTED
→ raw_packet_ref = null

CACHE_WRITE_FAILED
→ raw_packet_ref = null
```
## 2. 加入上下文队列流程
队列结构：Map<sender_id, Deque<ContextSlot>>
同一sender_id的数据包从任务接入模块到上下文队列的提交过程串行执行。前一个数据包完成ContextSlot追加后，才处理下一个数据包的入队。不同sender_id之间可以并行处理。

根据sender_id找到对应的上下文队列
→ 队列不存在时创建该sender_id的空队列
→ 建立ContextSlot时检查end_generate_timestamp_ns
→ 按本节整体流程设置PENDING或VALIDATION_REJECTED
→ 将ContextSlot原子追加到队尾
→ 只有PENDING位置继续严格数据校验

## 3. ContextSlot的创建和更新
创建且时间戳合法
→ PENDING，raw_packet_ref=null

时间戳或严格校验失败
→ VALIDATION_REJECTED，raw_packet_ref=null

缓存成功
→ AVAILABLE，raw_packet_ref有效

缓存失败
→ CACHE_WRITE_FAILED，raw_packet_ref=null
# 二、校验原始数据

## 1. 校验哪些字段和通道

### 1.1 包级字段
| 字段 | 校验内容 |
|---|---|
| `data` | 必须存在且为对象 |

### 1.2 必须存在的数据通道
| 通道 | 采样率 | 点数 | 需要检查的字段 |
|---|---:|---:|---|
| `vibration` | 64000 Hz | 3200 | `unit`、`sample_rate_hz`、`sample_count`、`values` |
| `phase_current_1_A` | 64000 Hz | 3200 | `unit`、`sample_rate_hz`、`sample_count`、`values` |
| `phase_current_2_A` | 64000 Hz | 3200 | `unit`、`sample_rate_hz`、`sample_count`、`values` |
| `shaft_speed_rpm` | 4000 Hz | 200 | `sample_rate_hz`、`sample_count`、`values` |
| `load_torque_nm` | 4000 Hz | 200 | `sample_rate_hz`、`sample_count`、`values` |
| `bearing_radial_load_n` | 4000 Hz | 200 | `sample_rate_hz`、`sample_count`、`values` |
| `bearing_module_temperature_c` | 单值 | 1 | 必须为有限数值；配置了温度允许范围时再执行范围检查 |

### 1.3 每路序列的具体检查
对六路序列分别检查：
1. 通道字段存在；
2. 通道内容是对象；
3. sample_rate_hz是整数；
4. sample_count是整数；
5. values是一维数组；
6. values不能为空；
7. 声明的采样率符合当前配置；
8. 声明的采样点数符合当前配置；
9. values实际长度等于sample_count；
10. 每个元素都是数值；
11. 不包含NaN、正负Inf；
12. 配置了硬性允许范围的通道，数值没有超出该范围；本阶段未取得权威量程时该检查停用。

单位合法值：
vibration.unit必须为mm/s；
phase_current_1_A.unit必须为A；
phase_current_2_A.unit必须为A。
## 2. 按什么顺序校验
遇到第一个错误就立即返回，固定校验顺序：
```text
1. 检查data
2. 检查六路序列和温度字段是否齐全
3. 检查字段类型、通道对象和values数组结构
4. 检查振动和两路电流的单位
5. 检查各通道sample_rate_hz
6. 检查各通道sample_count
7. 检查values是否为空以及实际长度
8. 检查所有序列值和温度是否为有限数值
9. 按统一配置检查硬性数值范围
10. 全部通过后返回success=true、error_code=null，任务编排器继续把当前原始包交给缓存模块。
```
六路通道内部也应固定顺序：
```text
vibration
→ phase_current_1_A
→ phase_current_2_A
→ shaft_speed_rpm
→ load_torque_nm
→ bearing_radial_load_n
→ bearing_module_temperature_c
```
## 3. 校验完成的返回

校验成功返回：
| 返回项 | 取值 |
|---|---|
| `success` | `true` |
| `error_code` | `null` |

校验失败返回：
| 返回项 | 取值 |
|---|---|
| `success` | `false` |
| `error_code` | 对应的稳定错误码 |

错误码：
| 错误码 | 含义 |
|---|---|
| `REQUIRED_FIELD_MISSING` | 必要字段或通道缺失 |
| `INVALID_FIELD_TYPE` | 字段、通道对象、数组结构或数组元素的类型不合法 |
| `EMPTY_CHANNEL_VALUES` | 通道数组为空 |
| `INVALID_CHANNEL_UNIT` | 单位不符合约定 |
| `INVALID_SAMPLE_RATE` | 采样率错误 |
| `INVALID_SAMPLE_COUNT` | 声明的采样点数错误 |
| `SAMPLE_COUNT_MISMATCH` | 实际数组长度与声明不一致 |
| `NON_FINITE_VALUE` | values中存在NaN或正负Inf |
| `VALUE_OUT_OF_RANGE` | 数值超出已配置的硬性范围（仅对已配置范围的通道启用） |
| `INVALID_TIMESTAMP` | 采集结束时间缺失或格式非法 |

# 三、把合法原始包写入环形缓存

只有第二部分严格校验成功的原始数据包，才能进入环形缓存。

同一 `sender_id` 的缓存提交按接收顺序串行执行，不同 `sender_id` 可以并行写入。

## 1. 缓存保存什么
环形缓存中的每个有效位置，直接保存一个通过严格校验的完整`ValidatedRawPacket`。

缓存中的对应关系为：

```text
raw_packet_ref
→ ValidatedRawPacket
```
- ValidatedRawPacket是通过第二部分严格校验的完整原始数据包；
- raw_packet_ref是读取该原始包的逻辑缓存键；
- raw_packet_ref保存在ContextSlot中，不属于原始数据包内容；
- received_at_ns已经保存在ContextSlot中，用于确定接收顺序和执行60秒淘汰，不需要在原始缓存中重复保存。

ValidatedRawPacket完整保存：
| 内容 | 保存字段 |
|---|---|
| 数据包身份 | `task_id`、`packet_id`、`sender_id`、`sequence_number` |
| 采样时间 | `end_generate_timestamp_ns` |
| 三路高采样率数据 | `vibration`、`phase_current_1_A`、`phase_current_2_A` |
| 三路低采样率数据 | `shaft_speed_rpm`、`load_torque_nm`、`bearing_radial_load_n` |
| 温度 | `bearing_module_temperature_c` |
| 通道采样信息 | 各通道的`sample_rate_hz`、`sample_count`和`values`，振动和两路电流另外保存unit |

## 2. 如何生成`raw_packet_ref`

`raw_packet_ref`是完整原始包的逻辑缓存键。

它负责建立下面的查询关系：

```text
ContextSlot.raw_packet_ref
→ 原始环形缓存
→ ValidatedRawPacket
```

`raw_packet_ref`只需要在对应`ContextSlot`仍然有效期间保持唯一和稳定。数据被淘汰后，该值同时失效。

当前阶段使用以下字段组合生成`raw_packet_ref`：

```text
(sender_id, task_id, sequence_number)
```

其中：

| 字段 | 作用 |
|---|---|
| `sender_id` | 确定原始数据属于哪个发送器的缓存分区 |
| `task_id` | 确定数据包所属任务 |
| `sequence_number` | 确定数据包在任务中的序号位置 |

上游任务接入模块已经保证：
```text
同一个task_id中
一个sequence_number只对应一个实际数据包
```
因此，加入`sender_id`后，可以在边缘原始缓存中唯一确定当前数据包。

raw_packet_ref在逻辑上由sender_id、task_id和sequence_number组成。内部实现优先使用不可变复合键，不要求编码为字符串；需要记录日志或跨接口传输时，可以转换为统一格式的字符串。
复合键：
```text
(sender_01, task_000001, 37)
```
字符串：
```text
sender_01/task_000001/37
```

### 生成流程

`raw_packet_ref`由任务编排器在严格校验成功后、调用环形缓存模块前生成。

```text
严格校验成功
→ 根据sender_id、task_id和sequence_number生成raw_packet_ref
→ 将raw_packet_ref和ValidatedRawPacket一起交给环形缓存模块
```

此时不能立即修改`ContextSlot.raw_packet_ref`。

只有原始包完整写入缓存后，才能执行：

```text
ContextSlot.raw_packet_ref = 当前raw_packet_ref
ContextSlot.cache_status = AVAILABLE
```

如果写入失败：

```text
丢弃本次生成的raw_packet_ref
→ ContextSlot.raw_packet_ref保持为null
→ ContextSlot.cache_status = CACHE_WRITE_FAILED
```

这样可以保证：

```text
ContextSlot.raw_packet_ref不为null
→ 一定能够从原始缓存中读取到完整ValidatedRawPacket
```

### 重复键处理

写入缓存前必须检查当前`raw_packet_ref`是否已经存在。

正常情况下，上游已经过滤重复包，因此不应出现重复缓存键。

如果缓存中已经存在相同的`raw_packet_ref`：

```text
禁止覆盖原有ValidatedRawPacket
→ 本次写入失败
→ 返回success=false
→ error_code=RAW_CACHE_WRITE_FAILED
→ 在本地日志中记录缓存键冲突
```

不能用新数据静默覆盖已有原始包，否则已有`ContextSlot`可能读取到错误数据。

### 禁止使用的引用方式

`raw_packet_ref`不能直接使用：

- 环形数组的物理下标；
- 对象内存地址；
- `packet_id`单字段；
- `end_generate_timestamp_ns`单字段。

环形数组的物理位置会被循环复用，不能作为稳定引用。

`packet_id`可能在不同任务中重复，`end_generate_timestamp_ns`也不能单独保证数据包身份唯一，因此二者只用于云端请求到达后的锚点定位和身份核对，不作为原始缓存的唯一查询键。

### 模块返回结构

任务编排器在调用环形缓存模块前已经生成并持有`raw_packet_ref`，因此缓存模块不需要返回该字段。

环形缓存模块仍然只返回：

| 返回字段 | 成功 | 失败 |
|---|---|---|
| `success` | `true` | `false` |
| `error_code` | `null` | `RAW_CACHE_WRITE_FAILED` |

缓存成功后，由由上下文管理器将已经生成的`raw_packet_ref`写入`ContextSlot`；缓存失败时，该值不写入`ContextSlot`。

## 3. 如何保证完整包原子写入
当前阶段为每个`sender_id`维护一把普通互斥锁。

该互斥锁与发送器的缓存状态一起创建并长期复用：

```text
SenderCacheState
├── ContextSlot队列
├── 原始数据环形缓存
└── mutex
```
同一个sender_id的ContextSlot追加、缓存写入、上下文查询和缓存淘汰，都必须使用同一把互斥锁。不同sender_id使用不同的互斥锁，可以并行处理。
写入流程：

```text
在缓存外准备完整的ValidatedRawPacket缓存副本
→ 接收任务编排器已经生成的raw_packet_ref
→ 获取当前sender_id的mutex
→ 检查ContextSlot.cache_status仍为PENDING
→ 检查ContextSlot.raw_packet_ref仍为null
→ 检查raw_packet_ref不存在
→ 检查缓存容量和可写位置
→ 一次性写入完整ValidatedRawPacket
→ 建立raw_packet_ref到ValidatedRawPacket的查询关系
→ 由上下文管理器设置ContextSlot.raw_packet_ref = 当前raw_packet_ref
→ 由上下文管理器设置ContextSlot.cache_status = AVAILABLE
→ 释放mutex
```
cache_status = AVAILABLE必须最后设置。它一旦对外可见，raw_packet_ref就必须能够读取到完整原始包。

写入失败和回滚:
回滚只能处理本次写入新建的数据，不能删除相同缓存键原来对应的数据。

写入失败时：
```text
如果本次已经建立查询关系：
→ 删除本次建立的raw_packet_ref查询关系

如果本次已经写入ValidatedRawPacket：
→ 删除本次写入的ValidatedRawPacket

如果当前ContextSlot仍然处于PENDING：
→ ContextSlot.raw_packet_ref保持为null
→ ContextSlot.cache_status = CACHE_WRITE_FAILED

→ 释放mutex
→ 返回success=false
→ error_code=RAW_CACHE_WRITE_FAILED
```
如果写入前发现raw_packet_ref已经存在：
不覆盖已有ValidatedRawPacket
→ 不删除已有查询关系
→ 不修改已经处于AVAILABLE的ContextSlot
→ 在本地日志中记录缓存键冲突
→ 返回success=false
→ error_code=RAW_CACHE_WRITE_FAILED

互斥锁：

- 一把锁对应一个`sender_id`；
- 和`SenderCacheState`一起创建；
- ContextSlot追加、写入、查询、淘汰共用；
- 不同发送器互不阻塞。

## 4. 如何保证缓存内容不被降采样修改

写入环形缓存时，必须为`ValidatedRawPacket`建立缓存专用深拷贝。

深拷贝必须包含六路通道中的`values`数组，不能只复制最外层对象。

数据使用关系如下：

```text
ValidatedRawPacket
├── 缓存专用深拷贝 → 写入环形缓存，只读保存
└── 独立计算数据   → 交给降采样、感知和模型
```
需要遵守以下规则：
写入缓存的ValidatedRawPacket不可修改；
降采样模块不能获得缓存内部数组的可写引用；
滤波、降采样、归一化和特征计算只能操作独立计算数据；
从缓存读取原始包时，只能返回只读数据或新的深拷贝；
缓存模块只提供写入、读取和淘汰操作，不提供修改原始包的操作。
这样可以保证从缓存读取的原始数据始终与写入时一致。

# 四、处理校验失败和缓存写入失败

ContextSlot按照第一部分的统一规则更新；PacketRecord、错误码、摘要和计数按照《任务接入和数据匹配实现流程》处理。单包失败不影响其他数据包。

# 五、缓存成功后交给后续处理流程

缓存成功后，任务编排器将当前包交给降采样、感知和边缘模型流程。本篇文档只说明流程交接，不展开后续模块的内部实现。
# 六、云端请求前20包时如何查询

上下文请求管理器接收云端请求，并调用上下文队列和原始缓存完成查询。

## 1. 请求字段

| 字段 | 含义 |
|---|---|
| `request_id` | 上下文请求编号 |
| `sender_id` | 目标发送器，也是缓存分区依据 |
| `anchor_packet_id` | 触发云端复核的数据包编号 |
| `anchor_end_generate_timestamp_ns` | 锚点包的采集结束时间 |
| `before_packet_count` | 需要读取的前置包数，当前固定为20 |
| `requested_at_ns` | 云端发出请求的时间，不参与锚点定位 |

所有字段必须存在，且`before_packet_count`必须等于20。请求不合法时返回`INVALID_CONTEXT_REQUEST`，不执行查询。

## 2. 定位锚点并读取前20包

```text
根据sender_id找到SenderCacheState
→ 获取该sender_id的mutex
→ 先执行过期数据淘汰
→ 在ContextSlot队列中查找同时满足以下条件的位置：

   ContextSlot.end_generate_timestamp_ns
   == anchor_end_generate_timestamp_ns

   并且

   ContextSlot.packet_id
   == anchor_packet_id
```

匹配结果：

```text
0个匹配
→ ANCHOR_NOT_FOUND

超过1个匹配
→ ANCHOR_NOT_UNIQUE

唯一匹配
→ 记录锚点位置anchor_index
→ 读取queue[anchor_index-before_packet_count : anchor_index]
```

查询不按照`task_id`过滤，可以跨越任务边界。锚点包本身不包含在返回结果中。

不可用位置不能使用更早的数据包补齐。

## 3. 判断查询结果

按照以下顺序判断：

```text
锚点前不足20个实际接收位置
→ INSUFFICIENT_CONTEXT

前20个位置中存在VALIDATION_REJECTED或CACHE_WRITE_FAILED
→ INSUFFICIENT_CONTEXT

前20个位置中存在PENDING
→ PENDING_CONTEXT

前20个位置全部为AVAILABLE
→ COMPLETE
```

`PENDING_CONTEXT`表示原始包仍在校验或写入缓存，由上下文请求管理器稍后重试。

`INSUFFICIENT_CONTEXT`表示当前无法取得完整20包，但仍然返回其中可以读取的原始包，并说明不可用位置。

## 4. 返回结果

查询结果至少包含：

| 字段 | 含义 |
|---|---|
| `request_id` | 对应的上下文请求编号 |
| `sender_id` | 数据发送器编号 |
| `anchor_packet_id` | 锚点包编号 |
| `anchor_end_generate_timestamp_ns` | 锚点包采集结束时间 |
| `expected_count` | 预期包数，当前固定为20 |
| `available_count` | 实际读取到的完整原始包数量 |
| `context_status` | 本次上下文查询状态 |
| `unavailable_packets` | 前20个位置中不可用的数据包信息 |
| `packets` | 按接收顺序从旧到新排列的完整原始包 |

`context_status`取值：

| 状态 | 含义 |
|---|---|
| `COMPLETE` | 前20个位置的完整原始包都可以读取 |
| `PENDING_CONTEXT` | 前20个位置中有原始包仍在处理，需要稍后重试 |
| `INSUFFICIENT_CONTEXT` | 锚点前不足20个位置，或其中存在永久不可用位置 |
| `ANCHOR_NOT_FOUND` | 没有找到对应锚点 |
| `ANCHOR_NOT_UNIQUE` | 找到多个匹配位置，无法唯一确定锚点 |
| `INVALID_CONTEXT_REQUEST` | 请求字段或`before_packet_count`不合法 |

完成数据读取或复制后释放`mutex`。网络发送过程不能继续占用该互斥锁。

# 七、如何淘汰超过保留时间的数据

## 1. 过期判断

保留时间按照`ContextSlot.received_at_ns`计算：

```text
当前边缘时间 - received_at_ns
>= raw_cache_retention_seconds
→ 当前位置已经过期
```

`end_generate_timestamp_ns`只用于锚点定位，不参与缓存淘汰。

## 2. 淘汰触发时机

以下情况都需要检查并淘汰过期数据：

- 新数据包加入上下文队列时；
- 云端上下文查询开始前；
- 后台定期清理时。

淘汰操作必须先获取对应`sender_id`的`mutex`。

## 3. 淘汰流程

上下文队列按照接收时间排列，因此从队头开始检查：

```text
获取当前sender_id的mutex
→ 检查队头ContextSlot
→ 未过期：停止检查
→ 已过期：删除该ContextSlot

如果raw_packet_ref不为null：
→ 删除raw_packet_ref到ValidatedRawPacket的查询关系
→ 释放对应的完整ValidatedRawPacket

→ 继续检查下一个队头
→ 释放mutex
```

`ContextSlot`和对应原始包必须在同一次淘汰操作中删除，不能留下悬空引用或无人引用的原始包。

## 4. 任务边界不触发淘汰

缓存按照`sender_id`和保留时间管理，不按照`task_id`管理。

因此：

- 任务结束时不能清空缓存；
- 新任务开始时不能清空上一任务的数据；
- 只要数据尚未过期，就可以作为跨任务上下文使用。

## 5. 容量不足处理

写入前先淘汰已经过期的数据。

如果清理后仍然没有可写位置：

```text
禁止提前淘汰尚未达到保留时间的数据
→ 本次缓存写入失败
→ 返回RAW_CACHE_WRITE_FAILED
→ 在本地日志中记录缓存容量不足
```
队列和原始缓存容量应在系统启动时按照第九部分的配置要求进行检查，不能静默使用不足以保证保留时间的容量。

# 八、并发和一致性怎么保证

## 1. 共享数据操作规则

同一个`sender_id`的以下操作必须使用同一把`mutex`：

- 追加`ContextSlot`；
- 提交完整原始包；
- 查询上下文；
- 淘汰过期数据。

不同`sender_id`之间可以并行执行。

数据校验、降采样、模型推理和网络发送不操作共享缓存，不需要持有该互斥锁。

## 2. 固定查询快照

上下文查询需要在持有`mutex`期间完成：

```text
定位锚点
→ 确定前20个ContextSlot
→ 记录不可用位置信息
→ 复制可用的ValidatedRawPacket
→ 形成固定查询快照
→ 释放mutex
```

后续网络发送只使用查询快照，不能继续读取环形缓存。

这样可以保证查询完成后，即使新包到达或旧包被淘汰，已经选定的前20个位置和原始数据也不会发生变化。

## 3. 一致性要求

系统必须始终满足：

```text
一个实际收到的唯一数据包
→ 最多建立一个ContextSlot

cache_status = AVAILABLE
→ raw_packet_ref有效
→ 能够读取完整ValidatedRawPacket

cache_status不是AVAILABLE
→ raw_packet_ref = null

ContextSlot被淘汰
→ 对应查询关系和ValidatedRawPacket同时删除
```

任何异常都必须释放`mutex`，避免同一发送器后续写入、查询和淘汰被永久阻塞。

# 九、配置和验收标准

## 1. 缓存和上下文配置

| 配置项 | 当前要求 |
|---|---|
| `raw_cache_retention_seconds` | 不小于60秒 |
| `max_receive_rate_per_sender` | 当前固定20包/秒 |
| `context_queue_capacity_per_sender` | 不小于1200个位置，并预留一定余量 |
| `raw_cache_capacity_per_sender` | 不小于1200个完整原始包，并预留一定余量 |
| `context_before_packet_count` | 固定为20 |
| `cache_cleanup_interval_seconds` | 大于0，当前建议1秒 |

最小容量按照下面的公式计算：

```text
最小容量
= max_receive_rate_per_sender
× raw_cache_retention_seconds
```

当前每50 ms接收一包，因此：

```text
20包/秒 × 60秒 = 1200包
```

队列容量按照全部实际数据包计算，原始缓存容量按照全部数据包都校验成功的最坏情况计算。

## 2. 数据校验配置

| 通道 | 采样率 | 采样点数 | 单位要求 |
|---|---:|---:|---|
| `vibration` | 64000 Hz | 3200 | `mm/s` |
| `phase_current_1_A` | 64000 Hz | 3200 | `A` |
| `phase_current_2_A` | 64000 Hz | 3200 | `A` |
| `shaft_speed_rpm` | 4000 Hz | 200 | 当前不检查`unit` |
| `load_torque_nm` | 4000 Hz | 200 | 当前不检查`unit` |
| `bearing_radial_load_n` | 4000 Hz | 200 | 当前不检查`unit` |
| `bearing_module_temperature_c` | 单值 | 1 | 必须为有限数值；配置了温度允许范围时再执行范围检查 |

六路序列和温度的硬性允许范围根据传感器接口和实际量程统一配置，不能散落在校验代码中。本阶段尚未取得权威量程边界，允许系统在缺少范围配置时启动：未配置范围的通道不执行`VALUE_OUT_OF_RANGE`校验，也不能编造范围值；已配置范围的通道必须按其范围校验。启动日志需记录当前量程范围的配置情况。

每个范围至少包含：

```text
允许最小值
允许最大值
```

## 3. 启动配置检查

边缘启动时必须检查：

```text
raw_cache_retention_seconds >= 60
context_before_packet_count = 20
context_queue_capacity_per_sender满足最小容量
raw_cache_capacity_per_sender满足最小容量
cache_cleanup_interval_seconds > 0
各通道采样率和采样点数配置完整
需要检查单位的通道已经配置合法单位
配置了硬性允许范围的通道其范围合法；本阶段未取得硬量程时允许缺少范围配置并跳过`VALUE_OUT_OF_RANGE`校验，但需在启动日志中记录该能力缺失
```

任一必要配置缺失或不合法时，边缘不能静默使用默认值继续运行，应记录配置错误并停止启动当前处理流程。

## 4. 验收标准

| 验收场景 | 预期结果 |
|---|---|
| 合法完整包进入模块 | 建立一个`ContextSlot`，校验成功并完整写入原始缓存 |
| 必要字段或通道缺失 | 返回`REQUIRED_FIELD_MISSING`，不写入原始缓存 |
| 字段或数组类型错误 | 返回`INVALID_FIELD_TYPE` |
| 通道数组为空 | 返回`EMPTY_CHANNEL_VALUES` |
| 单位错误 | 返回`INVALID_CHANNEL_UNIT` |
| 采样率错误 | 返回`INVALID_SAMPLE_RATE` |
| 声明采样点数错误 | 返回`INVALID_SAMPLE_COUNT` |
| 数组实际长度不一致 | 返回`SAMPLE_COUNT_MISMATCH` |
| 包含NaN或正负Inf | 返回`NON_FINITE_VALUE` |
| 已配置硬量程且数值超出范围 | 返回`VALUE_OUT_OF_RANGE` |
| 未配置硬量程 | 不执行`VALUE_OUT_OF_RANGE`校验，仅检查有限数值 |
| 采集结束时间缺失或非法 | 返回`INVALID_TIMESTAMP` |
| 原始缓存写入失败 | 不留下原始包或查询关系，`ContextSlot`进入`CACHE_WRITE_FAILED` |
| 后续计算修改自己的数据 | 缓存中的`ValidatedRawPacket`内容保持不变 |
| 锚点前存在20个可用位置 | 返回20个按接收顺序排列的原始包和`COMPLETE` |
| 前20个位置跨越任务边界 | 不按`task_id`过滤，能够正常返回跨任务上下文 |
| 锚点前不足20个位置 | 返回现有可用包和`INSUFFICIENT_CONTEXT` |
| 前20个位置存在校验或缓存失败 | 不使用更早数据替代，返回`INSUFFICIENT_CONTEXT` |
| 前20个位置存在`PENDING` | 返回`PENDING_CONTEXT` |
| 找不到锚点 | 返回`ANCHOR_NOT_FOUND` |
| 找到多个相同锚点 | 返回`ANCHOR_NOT_UNIQUE` |
| 上下文请求字段非法 | 返回`INVALID_CONTEXT_REQUEST` |
| 数据尚未达到保留时间 | 不得被提前淘汰 |
| 数据达到保留时间并触发清理 | 删除ContextSlot、查询关系和完整原始包 |
| 任务结束或新任务开始 | 不清空尚未过期的数据 |
| 没有新包到达 | 后台定期清理仍能淘汰过期数据 |
| 缓存已满且没有过期数据 | 不提前淘汰旧包，本次写入返回`RAW_CACHE_WRITE_FAILED` |
| 查询同时发生写入或淘汰 | 查询快照保持不变，不出现半包、重复位置或悬空引用 |
| 不同发送器同时操作 | 分别使用自己的缓存状态和`mutex`，互不混用数据 |

完成以上验收后，可以认为校验、上下文队列和原始环形缓存已经满足第一阶段要求。
