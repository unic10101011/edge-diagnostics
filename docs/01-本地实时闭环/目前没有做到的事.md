## 一、阻断正式实施的问题

### 1. DeepSeek吞吐量可能无法满足20包/秒

感知流程规定：

- 每包覆盖50 ms；
- 每个发送器20包/秒；
- 当前按单包处理，不跨包聚合；
- 每包都进入边缘模型。

但[边缘模型运行实现流程.md](</D:/Projects/edge/docs/01-本地实时闭环/边缘模型运行实现流程.md:144>)里的`186.4 ms`只是示例，并非实测。如果真实推理耗时接近这个数，单并发理论吞吐量只有：

```text
1000 / 186.4 ≈ 5.36包/秒
```

明显低于20包/秒，而且还没有计算感知、HTTP、解析和日志耗时。

必须先决定：

- DeepSeek是否对每一个50 ms包执行；
- 是否只对规则发现的可疑包执行；
- 是否允许排队；
- 最大并发数；
- 最大队列长度；
- 队列满后直接使用代码路线，还是丢弃/延迟；
- 多发送器并发时的总容量；
- 目标硬件上的实际`p50/p95/p99`耗时。

如果坚持每包调用DeepSeek，必须先通过压测证明持续吞吐量不低于输入速率，否则文档流程在运行后必然积压。

这是当前最严重的问题。

### 2. `confidence`数值没有生成算法

当前文档让DeepSeek输出：

```json
{
  "confidence": 0.72
}
```

但没有说明`0.72`如何得到。[边缘模型运行实现流程.md](</D:/Projects/edge/docs/01-本地实时闭环/边缘模型运行实现流程.md:148>)又说明它是“未经校准的诊断分数”。

主接口则把它称为“当前诊断结果的置信度”，其他模块很可能会用它做：

```text
confidence >= 某阈值
```

目前必须在下面方案中选择一种：

1. DeepSeek自报分数  
   最容易闭环，但没有统计意义，只适合演示，其他模块不能当正确概率使用。

2. 代码规则计算分数  
   数值稳定、可重复，但必须说明模型类别与规则分数不一致时听谁的。

3. 当前阶段所有DeepSeek结果使用固定分数  
   不建议，因为不同输入返回相同分数，容易误导调度器。

4. 调度器暂时不使用置信度做关键决策  
   可以保留数值字段满足接口，但需要与调度器协商语义。

在确定算法前，`0.72`只能算示例值，不能写进实现代码。

### 3. 代码路线的`model_version`仍有语义冲突

主接口约定：

```text
model_version = 模型版本
```

当前实现流程建议代码路线返回：

```text
model_version = edge_rule_v1.0
```

这样虽然不增加字段，但把“规则版本”放进了“模型版本”字段。其他模块如果按模型版本解析、统计或上报，可能出现误解。

需要二选一：

- 协商确认`model_version`实际表示“产生当前诊断的模型或规则版本”，允许`edge_rule_v1.0`；
- 外部仍统一返回逻辑模型版本，规则版本和`execution_mode`只保存在内部日志。

第一种更容易追踪代码降级来源，但属于字段语义扩展，必须取得其他接口参与方确认。当前不能自行认定已经成立。

## 二、还需要确定的运行配置字段

### 模型服务与HTTP边界

文档只说明“WSL运行模型服务，Windows通过本机HTTP调用”，还缺少：

| 字段 | 需要确定的内容 |
|---|---|
| `model_endpoint` | 例如`http://127.0.0.1:8001/edge/infer` |
| `health_endpoint` | 模型存活检查地址 |
| `readiness_endpoint` | 权重加载和预热是否完成 |
| `connect_timeout_ms` | 建立HTTP连接超时 |
| `inference_timeout_ms` | 单包模型推理超时 |
| `max_concurrency` | 最大同时推理数量 |
| `request_queue_capacity` | 等待推理的最大包数 |
| `overload_policy` | 队列满时是否转代码路线 |
| `retry_count` | 模型失败是否重试；第一阶段建议0 |
| `service_startup_timeout_ms` | 等待模型服务启动的时间 |

代码替代执行器最好位于Windows边缘主进程，而不是放在同一个WSL模型服务里。否则WSL整体不可用时，模型和替代路线会一起失效。

### DeepSeek生成参数

至少要冻结：

```text
do_sample = false
max_new_tokens
dtype
device
local_files_only
prompt_version
prompt_sha256
```

还需要确定：

- 完整系统提示词；
- 是否允许DeepSeek输出思考文本；
- 如何定位最终JSON；
- 非法JSON是否重试一次；
- 是否允许修复JSON；
- 输出非法时立即降级还是重新生成；
- `reason_codes`允许哪些固定值；
- `recommended_actions`是自由文本还是固定枚举。

考虑20包/秒压力，最小闭环最好只让模型生成必要字段：

```json
{
  "edge_result": "warning",
  "confidence": 0.72,
  "edge_risk_level": "medium"
}
```

当前生成`reason_codes`、`evidence`和`recommended_actions`，最终又不进入外部`EdgeResult`。如果它们也不进入内部持久日志，就是无效生成，还会增加推理时延。

## 三、代码替代路线尚未达到可实现程度

[边缘模型运行实现流程.md](</D:/Projects/edge/docs/01-本地实时闭环/边缘模型运行实现流程.md:213>)目前只规定了代码路线的性质，没有具体规则。

必须确定：

```text
rule_version
使用哪些PerceptionResult字段
每项特征的warning阈值
每项特征的fault阈值
单项规则分数算法
多项规则合并算法
质量状态如何影响结果
edge_result映射
edge_risk_level映射
confidence规则分数
```

还缺少一个内部错误：

```text
CODE_FALLBACK_FAILED
```

它不一定要加入协商好的外部接口，但内部日志需要它。否则“两条路线都失败”时只能看到模型错误，无法知道代码路线为什么失败。

如果服务启动时就没有模型、只运行代码路线，而代码路线又失败，也需要明确最终映射成现有哪个外部错误码。若不增加外部字段，最接近的是：

```text
MODEL_INFERENCE_FAILED
```

但这仍需明确写成固定映射，不能由实现者临时选择。

## 四、输入字段还需要冻结成真正的数据契约

当前输入字段范围已经较清楚，但示例不是严格JSON：

- 包含注释；
- 工况字段值为空；
- 部分主接口示例存在缺少逗号；
- 没有类型、范围和可空规则。

不建议修改已经协商的接口字段，而是基于这些字段生成一份机器可校验的内部Schema或Pydantic模型。

需要冻结：

| 内容 | 需要确定 |
|---|---|
| 字段类型 | `float`、`int`、`str`、列表 |
| 必填性 | 哪些字段必须存在 |
| 可空性 | 是否允许`null` |
| 数值范围 | 如频率、比例、置信度 |
| 枚举 | 质量状态、诊断类别、风险等级 |
| 额外字段 | 是拒绝还是忽略 |
| 特征版本 | 模型如何确认收到正确版本的特征 |
| 单位 | 是否必须严格等于`mm/s`和`A` |

另外，[边缘模型运行实现流程.md](</D:/Projects/edge/docs/01-本地实时闭环/边缘模型运行实现流程.md:102>)说追踪字段不参与诊断，但漏写了：

```text
end_generate_timestamp_ns
```

它也应只用于追踪，不应进入DeepSeek诊断内容，除非以后明确使用时间趋势。

## 五、输出枚举仍不够严格

当前主接口写的是：

```text
normal、warning、fault等
```

“等”会让实现者不知道还能否输出其他类别。正式实现前必须固定为封闭枚举，例如：

```text
edge_result:
  normal
  warning
  fault
```

风险等级同样需要冻结：

```text
edge_risk_level:
  low
  medium
  high
```

失败时不产生`EdgeResult`，因此：

```text
output = null
```

而不是在成功结果里输出`not_assessed`，除非主接口明确要求。

还需要确定类别和风险能否自由组合。例如是否允许：

```json
{
  "edge_result": "normal",
  "edge_risk_level": "high"
}
```

如果不允许，应规定映射：

```text
normal  → low
warning → medium
fault   → high
```

如果允许，则要说明风险等级的独立算法。

## 六、版本字段目前存在格式不一致

当前文档同时出现：

```text
model_version = 1.0.0
model_version = edge_v1.0
rule_version = edge_rule_v1.0
```

需要确定一个统一规则。

建议区分：

```text
清单内部语义版本：
1.0.0

外部接口版本：
edge_v1.0
```

但必须明确两者映射，或者干脆统一为同一个值。否则心跳、任务输出、摘要和模型清单可能分别报告不同版本。

还需要补齐当前占位字段：

```text
base_model_revision
weights_sha256
prompt_sha256
实际pytorch_version
实际transformers_version
validated_at
```

在这些字段没有真实值之前，模型包还不能称为正式发布版本。

## 七、节点状态上报与降级状态不完整

主接口节点心跳包含：

```text
models[].model_version
models[].load_status
```

需要确定：

- 模型加载失败但代码路线可用时，`load_status`是什么；
- 节点是否仍接受任务；
- 规则路线可用性是否只写内部日志；
- 模型运行期间连续失败多少次后切换为长期`CODE_FALLBACK`；
- 恢复模型路线需要自动重试还是重启服务。

这不一定需要修改外部接口，但内部状态机必须确定。

## 八、还缺少正式验收标准

要成为正式执行计划，至少应列出以下验收用例：

- 模型目录不存在；
- 模型文件哈希不一致；
- 模型加载失败；
- 模型预热失败；
- HTTP连接失败；
- 推理超时；
- 返回非JSON；
- 缺少输出字段；
- 输出类别非法；
- `confidence`不是有限数或超出`0～1`；
- 模型失败、代码路线成功；
- 模型和代码路线都失败；
- 20包/秒持续输入不积压；
- 多发送器并发；
- WSL服务退出后主进程仍可走代码路线；
- 任务输出与主接口逐字段一致；
- 上云摘要映射逐字段一致。

## 最终判断

当前状态可以这样定性：

| 层级 | 当前状态 |
|---|---|
| 架构设计 | 基本可用 |
| 外部接口映射 | 基本对齐 |
| 模型运行详细设计 | 尚未完成 |
| 代码替代规则 | 尚未完成 |
| 性能与超时 | 尚未确定 |
| 可直接编码实施 | 暂时不建议 |
| 可作为正式验收依据 | 还不可以 |

最少需要先确定下面6项，才能升级为正式执行计划：

1. 每包是否都调用DeepSeek，以及20包/秒如何承载；
2. 模型HTTP端点、超时、并发和过载策略；
3. `confidence`的生成算法与其他模块的使用语义；
4. 代码替代阈值、分数算法和规则版本；
5. `model_version`能否承载`edge_rule_v1.0`；
6. 严格输入输出Schema和验收测试。
